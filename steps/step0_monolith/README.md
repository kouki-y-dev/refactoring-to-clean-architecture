# Step 0: Monolith

## Overview

EC サイトの注文システム（商品一覧、カート操作、注文確定、履歴参照）の全機能が、`main.py` という**単一のファイルにすべて詰め込まれた状態**です。

アーキテクチャやデザインパターンを一切考慮せず、「動くこと」だけを最優先に実装した初期コードとなっています。

```
steps/step0_monolith/
├── src/
│   └── main.py          # 全機能が1ファイルに集約
└── tests/
    ├── conftest.py       # テスト用パス設定
    └── test_main.py      # テストコード（テストの書きにくさを実感）
```

---

## How to Run

### アプリケーションの実行 (CLI)

```bash
uv run steps/step0_monolith/src/main.py
```

### テストの実行

```bash
uv run poe test-step steps/step0_monolith/tests
```

---

## Code Structure

- **データ層**: モジュールレベルのグローバル変数 (`products`, `carts`, `orders`) にインメモリの辞書（`dict`）として保持。
- **ロジック & UI**: 各関数 (`list_products`, `add_to_cart`, `place_order` など) が、辞書の直接読み書き・ビジネスロジックの計算・`print()` による画面出力を同時に行う。
- **エントリーポイント**: `main()` 関数で CLI の対話型メニューを実行。

## Problems & Challenges

### 1. 1か所の変更があらゆるところに影響する（密結合・変更容易性の欠如）
- カートや注文のデータ構造（辞書のキー名など）を少し変えただけで、すべての関数を修正する必要があります。
- どこを直せばいいのか、どこに影響が出るのかがパッと見で把握できません。

### 2. コードの重複が多い（DRY 原則の違反）
- 小計計算（`price * quantity`）、消費税計算（`* TAX_RATE`）、在庫チェックなどが、`view_cart`、`place_order`、`add_to_cart` など複数の関数に分散して書かれています。
- 税率の丸め方や在庫チェックの仕様が変わった場合、散らばったすべての箇所を探して修正しなければならず、修正漏れのリスクが高くなります。

### 3. 各関数の責務が混ざり合っている（単一責任の原則違反・関心の分離の欠如）
- 例えば `place_order()`（注文確定）の中では以下がすべて同居しています：
  1. 入力値やカートのバリデーション
  2. 在庫数チェック
  3. 小計・消費税・合計金額の計算
  4. 注文データの生成
  5. 在庫データの直接書き換え（減算）
  6. カートデータのクリア
  7. `print()` による標準出力
- 1つの関数が「ビジネスルール」「データ永続化」「ユーザーインターフェース」の3役を同時に担ってしまっています。

### 4. テストが極めて書きにくい（テスト容易性の低さ）
- **副作用のキャプチャが必須**: 関数が戻り値を返さず直接 `print()` するため、テストでは `capsys` を使って標準出力を文字列マッチングするしかありません。
- **単体テストができない**: ロジックだけを切り離してテストできず、常にグローバル状態や出力を含めた統合テストになってしまいます。
- **テスト間の汚染**: 各テストの実行前後にグローバル状態を手動（またはフィクスチャ）でリセットしないと、テスト順序によって成否が変わってしまいます。

### 5. グローバル状態への依存と隠れた副作用
- モジュールレベルの辞書をどこからでも自由に書き換えられるため、「いつ・誰が・どこで」状態を変更したのか追跡できません。
- マルチスレッド環境や複数リクエストを処理する Web アプリケーションへの拡張が不可能です。

### 6. データモデル（型）の不在とタイポのリスク
- すべてが素の `dict`（プリミティブな型）で扱われており、`"product_id"` や `"subtotal"` などのキー名のタイポを実行時まで検知できません。
- 不正な値（数量が負の数、在庫がマイナス等）を防ぐ一貫したバリデーションの仕組みが存在しません。

### 7. インフラや UI の差し替えができない
- 標準入出力（CLI）とビジネスロジックが直結しているため、「Web API (FastAPI 等) 化したい」「データベース (PostgreSQL / SQLite) に保存したい」となった場合に、コードをほぼ全書き直しする必要があります。

### 8. エラーハンドリングの不統一
- 異常系でも例外（Exception）を投げず、エラー文を `print()` して `return`（`None`）しているため、呼び出し元が処理の成功/失敗をプログラム的に判定できません。
