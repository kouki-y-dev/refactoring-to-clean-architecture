# Step 2: ドメインモデルの抽出 (Domain Model)

## 概要

Step 1 で関心の分離（UI / Service / Data Access）を行いましたが、データの受け渡しには依然として素の辞書（`dict`）が使われており、ビジネスルールが `service.py` に手続き的に記述されていました。

Step 2 では、**ドメインモデル（エンティティ・値オブジェクト）** を抽出し、データとビジネスルールをひとまとめにカプセル化しました。データモデルには **Pydantic (`BaseModel`)** を採用し、型安全性とバリデーションを強化しています。

```
steps/step2_domain_model/
├── src/
│   ├── domain/
│   │   ├── __init__.py
│   │   └── entity.py       # ドメインモデル（Product, Cart, Order 等）
│   ├── cli.py              # プレゼンテーション層（CLI）
│   ├── data_access.py      # データアクセス層（モデルの保持・取得）
│   ├── main.py             # エントリーポイント
│   └── service.py          # サービス層（ドメインモデルの操作・調整）
└── tests/
    ├── conftest.py          # テスト用フィクスチャ
    ├── test_cli.py          # CLI のテスト
    ├── test_data_access.py  # データアクセス層のテスト
    ├── test_domain.py       # ドメインモデル単体テスト
    └── test_service.py      # サービス層のテスト
```

## 構成とコードの解説

### 1. `src/domain/entity.py` (ドメイン層)
システムの中心となるビジネス概念・ルールを表現するエンティティと値オブジェクトを定義しています。外部のライブラリやフレームワーク（DB や UI）には一切依存せず、純粋な Python + Pydantic で構築されています。

- **`Product` (商品エンティティ)**:
  - `price: int = Field(ge=0)`, `stock: int = Field(ge=0)` により、不正な価格や負の在庫の生成を防ぎます。
  - `has_enough_stock(quantity)`: 指定された数量の在庫があるかを判定します。
  - `decrease_stock(quantity)`: 在庫不足時に `ValueError` を送出しつつ在庫を減算します。
- **`CartItem` / `Cart` (カートエンティティ)**:
  - `CartItem`: 数量（`quantity > 0`）を保持します。
  - `Cart`: カート内の商品操作を集約し、同一商品の数量加算 (`add_item`)、存在チェックを伴う削除 (`remove_item`)、全クリア (`clear`)、空チェック (`is_empty`) などの責務を持ちます。
- **`CartDetailItem` / `CartDetails` (カート集計・表示用モデル)**:
  - `frozen=True` で不変（イミュータブル）に設定された集計用データ構造です。
- **`OrderItem` / `Order` (注文エンティティ)**:
  - `frozen=True` により一度作成された注文明細や合計金額の改ざんを防ぎます。
  - `Order.create(...)` ファクトリメソッド: 小計・消費税（10%）・税込合計金額の計算ルールを集約し、常に整合性の取れた注文エンティティを生成します。

### 2. `src/service.py` (サービス層)
ドメインモデルとデータアクセス層を連携させるオーケストレーション（調停役）を担当します。
- 辞書のキーを直接操作して計算するのではなく、ドメインモデルのメソッド（`product.has_enough_stock()` や `cart.remove_item()`）やファクトリ（`Order.create()`）を呼び出します。
- ビジネスルールそのものはドメインモデルに委譲されているため、コードの見通しが向上しています。

### 3. `src/data_access.py` (データアクセス層)
- 素の `dict` ではなく、`Product`, `Cart`, `Order` といったドメインモデルのインスタンスをインメモリ辞書で管理・返却します。

### 4. `src/cli.py` (プレゼンテーション層)
- ドメインモデルの属性（`product.name`, `order.total` など）にアクセスして画面表示を行います。辞書のキーアクセスと異なり、エディタの補完が効き、タイポも検知できます。

### 5. `tests/test_domain.py` (ドメインモデル単体テスト)
- データベースやグローバル状態、UI に一切依存しない純粋なドメインロジックの単体テストです。
- バリデーション、計算ロジック、不変性（`frozen=True`）の検証を高速かつ網羅的に実行します。

## 前回 (Step 1) からの改善点

1. **ドメイン知識・ビジネスルールのカプセル化**
   - Step 1 では `service.py` に散らばっていた「在庫チェック」「税率計算」「カートの数量加算」などのルールが、ドメインモデル（`Product`, `Cart`, `Order`）の中に自然な形でカプセル化されました。
2. **Pydantic による型安全性とバリデーション**
   - 素の辞書（`dict`）の引き回しを廃止したことで、キー名のタイポ（例: `product["stok"]`）によるバグを防止できるようになりました。
   - `price >= 0` や `quantity > 0` などの制約がモデル生成時に自動検証され、不正なデータがシステム内に紛れ込むのを防ぎます。
3. **イミュータビリティ（不変性）の確保**
   - `Order` や `OrderItem`、`CartDetails` に `frozen=True` を設定したことで、作成後に意図せず金額や注文内容が変更されるリスクを排除しました。
4. **テスト容易性（Testability）の大幅な向上**
   - インフラやモックを必要としない純粋な単体テスト（`test_domain.py`）を作成できるようになり、ビジネスロジックの動作保証が極めて簡単かつ高速になりました。

## 現時点での問題点

ドメインモデルが確立された一方で、アーキテクチャ全体としてはまだ以下の課題が残っています。

1. **データアクセスへの直接依存（DIP 違反・密結合）**
   - `service.py` が `import data_access` で具象モジュールに直接依存しています。
   - データの保存先を「インメモリ」から「SQLite / PostgreSQL」などに変更したい場合、`service.py` 側のコード変更を余儀なくされます（上位モジュールが下位モジュールの実装詳細に依存している状態）。
2. **データ永続化の抽象化（Interface / Repository）の欠如**
   - 「データをどう保存・取得するか」という契約（インターフェース）が定義されていないため、サービス層が具体的なインメモリ辞書のアクセス関数に縛られています。
3. **サービス層のテストにおけるグローバル状態への依存**
   - `test_domain.py` は独立してテストできますが、`test_service.py` は依然として `data_access` のグローバル辞書を変更するため、テストごとに `conftest.py` で状態を初期化する必要があります（モックやフェイクの注入ができない）。

## 次に導入するもの (Step 3: Repository パターン)

次の **Step 3: Repository** では、データアクセス層との結合度を下げるために **Repository パターン** を導入します。

- **リポジトリインターフェースの導入**:
  - `ProductRepository`, `CartRepository`, `OrderRepository` などの抽象的なインターフェース（またはプロトコル）を定義します。
- **データアクセスの隠蔽**:
  - データの永続化方法（インメモリ、RDB、ファイルなど）をリポジトリの内部に隠蔽し、サービス層はリポジトリのインターフェース経由でのみデータを操作するようにします。
- **テストのさらなる容易化**:
  - テスト時にモックリポジトリやインメモリリポジトリを簡単に差し替えられる基盤を整えます。
